# v0.8 execution and release plan

The owner requested continuation through v0.8 after the measured CI rollout.
The scope remains the four existing Bluefin desktop channels. Heavy evaluation,
image parsing, builds, ISOs and VM qualification run on GitHub. Local work uses
small fixture tests, source edits and bounded metadata downloads only.

## Starting evidence

[The October 14 results](ci-rollout-results.md) record the protected merges and
authenticated hosted measurements. All four profiles passed exact-digest
security, isolated signing, fresh install, upgrade and rollback in
[38639819537](https://github.com/closure-labs/finite/actions/runs/38639819537).
The successor [38648164385](https://github.com/closure-labs/finite/actions/runs/38648164385)
demonstrated original next ISO reuse. The Cachix writer worked, but the observed
reader gain did not repay its complete job cost. Automatic writing remains off.

Repository VERSION was 0.7.0; the latest published GitHub release was v0.6.0.
The current desktop contract accepts hosted VM evidence. Physical observations
remain informational. Unresolved scanner advisories remain visible; historical
scanner match counts are not a new release eligibility rule.

## Implementation and experiments

| Work | Behavior and proof | Adoption condition |
| --- | --- | --- |
| Selective Cachix preparation | Four declared tools by default; optional `--include-proofs`; batched derivation/output and closure validation; keys only in final upload | Six hosted legacy/candidate preparation jobs measure complete costs; subsequent matched upload/readers must prove net benefit before enabling automatic writing |
| Image/qualification identity | Reviewed host-only VM/ISO inputs leave image identity; unknown helpers remain conservative; installer/test content and executable modes bind qualification | One schema migration accompanies the genuine v0.8 payload change; fresh main builds and qualification establish new identities |
| Image verification cost | Retain cold/warm immutable registry-pull timings and manifest/config/platform associations | A future retained local export must prove exact published-byte association and total export/import/verification benefit over five warm and one cold equivalent runs; production registry verification continues |
| Inventory and Grype DB transport | Existing separate opt-in implementations preserve native evidence and fresh DB/policy checks | Compare baseline, inventory-only and DB-only for the same immutable candidate before any combined/default rollout; leave flags off until measured |
| Exact whole-qualification reuse | Existing exact candidate/predecessor/context and age checks remain | Wait for a genuine eligible repeat candidate; never create a publication event solely to claim reuse |

Run hosted experiments from the reviewed revision. Their findings can inform
later defaults without blocking an otherwise qualified release. Measurement
failure cannot weaken build, signing or qualification gates.

## Release sequence

1. Merge the reviewed v0.8 batch through the protected queue after required
   source, Nix, documentation and image checks. Set public ISO preservation scope
   to all four channels before its main build starts. SecretSpec resolves public
   options from GitHub; local credential tasks use devenv and the pass provider.
2. Build VERSION 0.8.0 on main once. Require each exact candidate's current
   vulnerability policy, signature, fresh-install and upgrade/rollback phases,
   desktop aggregation and promotion. Preserve each original candidate ISO.
3. Validate small authenticated acceptance/publication receipts and current
   channel digest bindings. Do not download or hash large ISOs locally.
4. Dispatch release preparation for each channel at the same successful main
   revision, using its build run and empty `iso_run`. Each hosted preparation
   authenticates original ISO bytes and rescans the immutable candidate with a
   fresh vulnerability DB and current policy. Retain unsigned packets for review.
5. Present the four concrete packets and QA/security results at the ship gate.
   The live `release` environment requires reviewer `declarative-dale` and main.
   Preserve this protection. Approved jobs resolve only release-signing secrets,
   create new exact-source tags and produce signed draft releases.
6. Inspect draft assets/signature receipts, then publish the approved channels.
   Set standard Finite explicitly as GitHub's latest release. Preserve predecessor
   rollback deployments and record source, runs, digests, tags and asset hashes.

| Channel | Profile | v0.8 tag |
| --- | --- | --- |
| finite | bluefin-generic | finite-finite-0.8.0 |
| finite-next | bluefin-next | finite-finite-next-0.8.0 |
| finite-dev | bluefin-dx-generic | finite-finite-dev-0.8.0 |

Per-channel concurrency prevents one approval wait from blocking another
channel's unsigned packet. Release request checks reject wrong versions/channels,
invalid run identifiers and existing tags before expensive setup. Creating the
tag explicitly at the exact SHA prevents an existing or racing tag from silently
replacing the intended source revision.

## Current state

Public ISO preservation scope is now `all`, with preservation and optimized
small-job caches enabled. Automatic Cachix writing remains false; inventory, DB
and whole-qualification reuse remain unset/default false. The security-cache
experiment has its own two-generation-per-platform retention namespace.

Implementation and review merged in
[PR #165](https://github.com/closure-labs/finite/pull/165). The
[v0.8 main run](https://github.com/closure-labs/finite/actions/runs/38668576342)
is building all four profiles at `aeb59d95db7b93d497d4d3627632949e9b04df79`.
Release rescans, signed drafts and publication have not yet occurred.

[The first hosted pilots](v0.8-hosted-pilot-results.md) failed closed on concrete
measurement assumptions. Keep their corrections in a separate reviewed change
until all four release workflows capture this successful producer revision.
Pilot findings do not weaken release gates or enable defaults. v0.7 evidence
remains a baseline, not qualification of the new v0.8 payload.
