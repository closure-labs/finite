# v0.9.0 implementation and acceptance

The approved target is native bootc composefs with signed UKIs, Fedora shim,
MOK and systemd-boot for both `finite` and `finite-dev`. The sole conversion
target is Dale's workstation. This document is an execution record, not a
qualified migration procedure. `VERSION` remains `0.8.3-dev` until the release
inputs and qualification are ready; changing it now would request releases
from the existing OSTree pipeline.

## Backup execution

The selected destination is `/var/home/dale/Nextcloud/finite-backup`. Bootable
rescue media is available according to the operator. The operator explicitly
instructed this implementation to rely on Nextcloud's automatic upload once the
encrypted file is created in that folder. A server download is not required.

Create a private inventory from the repository:

```bash
python3 scripts/workstation/recovery-backup.py inventory \
  --work "$PWD/artifacts/workstation-recovery"
```

The operator narrowed the backup to small unique configuration and credentials.
Review `inventory.json` locally. It selects SSH/GPG keys, password stores,
keyrings, Home Manager flakes/locks, shell and application settings, account
credentials and selected user services. Documents, Downloads, repositories,
installed software, Nix packages, Flatpaks, Homebrew apps and build outputs are
outside this backup's scope. Configuration/key inputs measured 980,268 bytes
before adding the small root recovery capture. Use `inventory --include PATH`
for any additional small unique file. Input above 512 MiB is refused; the tool
also budgets archive, Nextcloud copy, full restoration and OS working space
before encrypting. Credential symlinks require explicit recovery handling so a
restoration test cannot accidentally use live keys.

For this inspected workstation, the interactive wrapper captures recovery
essentials from `/dev/nvme0n1` and `/dev/nvme0n1p8`, verifies the recorded ESP
PARTUUID and LUKS UUID, creates the encrypted backup and tests local restoration:

```bash
bash scripts/workstation/backup-local.sh
```

Each attempt uses a fresh private run directory under
`artifacts/workstation-recovery/runs`. It requires local sudo and age passphrase prompts. Password-store verification
selects one restored encrypted entry privately; optionally pass a specific entry
as the wrapper's first argument. The individual commands below are available
for inspection and recovery after an interrupted attempt.

From a local terminal, use `lsblk` to identify the whole disk and LUKS partition,
then run `capture-recovery.sh` as root, passing those two devices and a **new**
private output directory under the home directory. This script reads disk state,
copies the LUKS header, unique boot-signing keys and EFI configuration, and
records firmware/mount information. It also captures selected account, SSH and
NetworkManager configuration. It
does not modify the disk or firmware. Keep these plaintext recovery files out of
Nextcloud. Add their directory to the inventory and ensure the calling user can
read it before encryption; root-owned key material must remain protected.

Quiesce applications writing important files, then run:

```bash
python3 scripts/workstation/recovery-backup.py create \
  --inventory "$PWD/artifacts/workstation-recovery/inventory.json" \
  --work "$PWD/artifacts/workstation-recovery"
```

`age` prompts locally for the recovery passphrase. Store it independently of
Nextcloud. This writes only an encrypted compressed archive, along with private
inventory/permission/owner-trust metadata. No plaintext archive is created.
The command copies only ciphertext into the selected Nextcloud folder under a
content-derived filename. Nextcloud handles the upload automatically. Test
local restoration with:

```bash
python3 scripts/workstation/recovery-backup.py verify \
  --work "$PWD/artifacts/workstation-recovery" \
  --pass-entry an-existing-password-entry
```

The verification compares the local and Nextcloud-folder bytes, decrypts/extracts in a private
temporary directory, checks credential permissions and numeric ownership,
imports saved owner-trust into the restored GPG home and tests password-store
decryption against restored keys without printing password contents. A failed
check produces no success receipt. Remove the private restored files after
manual recovery inspection if an interrupted verification leaves them behind.
The receipt records the operator's upload assumption; it does not authorize
disk changes by itself.

This is configuration/key recovery, not a disk-image or document backup. Rescue
media and verified release artifacts supply the reproducible OS/EFI binaries.

Backup completed on 2026-11-17: 17.7 MiB of selected inputs, including the root
recovery capture. The encrypted archive is 16,977,241 bytes with SHA256
`35c646849413ee35ef4226f7b9445ef4fb8101c3af6687ca60821d819c06f240`.
The local success receipt confirms restored credential modes/ownership and
password-store decryption using restored GPG keys. The encrypted file is in
the selected Nextcloud folder; successful automatic upload is assumed as
instructed. No server download is required.

## Production signing and image construction

The selected signing location is a protected CI signing service. Production
boot-signing credentials are separate from VM/trial and container-signing
keys. The dedicated main-only signer and public certificate are now provisioned;
see [boot signing, recovery and rotation](boot-signing.md). The identity is not
yet qualified for a production release.

Both recipes now select native composefs, generate a native crypt/FIDO2
initramfs, preserve upstream kernel/module provenance and omit bootupd. The
OSTree-only first-boot job and rpm-ostreed daemon have native-boot guards.
Recipe schema validation succeeds for both profiles. Full profile builds and
boot qualification of these changed recipes have not yet completed.

The sealing pipeline is implemented in `scripts/bluebuild/seal-native.py`:

- The canonical bootc 1.17.1 importer is built from the exact upstream commit,
  source hash and Cargo dependency hash in `sources/native-bootc.json`. Its
  binary hash is independently pinned alongside the Fedora importer. Nix locks
  ukify, sbsigntools, libfaketime, umoci and supporting tools.
- Signing runs outside the builder/image. The protected main-only
  `boot-signing.yml` workflow resolves the production key for one signer child.
  That child removes it from the environment before invoking subprocesses and
  deletes its private temporary key file on exit. Public certificates only
  enter OCI layers; signing work and large archives stay outside uploaded
  evidence.
- Deterministic OCI layers preserve source filesystem metadata. The loader is
  signed first; the canonical OCI import supplies the bootable-root digest for
  the signed UKI. An independent fresh import of the completed image must match
  every signed UKI's strict digest. Mounted-directory digest calculations and
  optional fs-verity are not accepted.
- Production publication now builds a raw root, seals it in the protected job,
  verifies the assembled sealed image, then applies the existing security,
  Cosign, encrypted-VM and promotion gates. Evidence binds raw and final
  registry digests, source/archive hashes, profile, build identity, certificate
  and importer. Resume requires the original successful raw-build and signing
  jobs and the original production receipt. Promotion rejects a raw native
  image even if older-style acceptance evidence is supplied.

The sealer was run twice against the disposable Fedora VM input, using only its
VM key. Both complete archives were byte-identical: SHA256
`d46e61157e9bc0da25d15b2ff7b030e46a4524286beb2158579d5129d7046374`.
Independent imports produced the same strict root digest. Local reports are
`artifacts/native-sealer-reproducibility.json` and
`artifacts/native-seal-fixture-7/sealed.json`. The Nix-built importer also
reproduced the earlier Fedora importer result on the original VM artifact.
These are tool/fixture integrity results, not encrypted production-profile
qualification or hardware migration acceptance. Production-key CI sealing has
not run. On 2026-11-18 UTC the sealed fixture also completed a fresh installation
and boot with Secure Boot, kernel lockdown, enforcing SELinux, required
fs-verity and zero failed units. Evidence is
`artifacts/native-sealer-boot/qualification.json`. The VM used 3 GiB and was
shut down after testing.

The independent checker in `scripts/bluebuild/verify-native-oci.py` pins the
importer version/hash, validates the reviewed certificate and every UKI
signature, and rejects ambiguous, optional or OSTree root arguments. It accepts
only the verified V1 digest format. A future V2 compatibility fallback requires
explicit verification of both digests.

`finite-efi-update.service` maintains packaged Fedora shim/MokManager and the
signed loader through a root-private recovery journal outside the ESP. The
shim-chain filename is `EFI/finite/grubx64.efi`. Fallback management defaults
off during coexistence; neither BootOrder nor old GRUB/rEFInd files are changed.
Synthetic tests interrupt every managed-file write, restore complete previous
generations, reject unknown external changes and insufficient space, and check
idempotence. The scratch-FAT VM test also recovered all seven interrupted writes and a
committed generation after remount, with a clean filesystem check. Firmware,
SBAT and loader-version-change qualification remains required. See [EFI updates and recovery](efi-updates.md).

On 2026-11-17 both live legacy channels had keyless signatures from the exact
`attest-image.yml@refs/heads/main` identity. Their immutable digests were
verified with Cosign, including transparency-log verification. The reviewed
`sources/legacy-registry-signatures.json` authorizes that identity only for
read-only predecessor authentication at those exact profile/digest pairs.
There is no verification-failure fallback. New candidates, installed update
policy, media verification and release promotion continue to require
`cosign.pub`. Legacy signature authentication does not qualify an unsupported
OSTree-to-native update or provide the required native upgrade baseline.

## Exact migration rehearsal

Before host partition changes, build an encrypted Btrfs VM with the recorded
partition layout and OSTree/GRUB arrangement. Use only file-backed VM devices.
Clone its disk before each failure injection. The current unencrypted ext4 VM
fixture does not meet this requirement.

The rehearsal must demonstrate:

- Distinct old and new root subvolumes in the same LUKS filesystem; shared user
  data and persistent Nix state remain accessible with the same numeric owners.
- Explicit old-root selection in the preserved GRUB boot entry, and signed
  native root-subvolume discovery/unlock without overriding a signed UKI's
  authenticated command line.
- Offline shrink in order: Btrfs filesystem, encrypted mapping, partition.
  Derive sector boundaries from the recorded geometry; verify sizes at every
  boundary before creating the 4 GiB VFAT XBOOTLDR on the same disk.
- Isolated installation staging mounts, preserving the old EFI directories,
  GRUB recovery path and BootOrder. Never run `to-existing-root` on the old root.
- Selected account/configuration migration, including numeric UID/GID values;
  no wholesale `/etc` copy, OSTree mounts or OSTree service activation.
- Recovery from interruption during shrink/staging/EFI writes, failed native
  boot selection, intact data, and successful return to the old system.

No shrink/install automation is authorized to run on hardware before these
results exist. If coexistence, root discovery or the old boot path fails, stop
the migration rather than substituting an internal reinstall.

## Qualification and hardware acceptance

For each exact release profile/artifact, retain authenticated results for fresh
encrypted installation; enforcing Secure Boot/SELinux/fs-verity; real kernel
and loader version upgrades; image rollback; configuration persistence; loaded
signed ZFS/v4l2loopback modules; tampered image rejection; insufficient-space
handling; and rescue recovery. Bind results to source revision, image digest,
ISO checksum, signing certificates and tool versions. Existing revision-marker
updates are insufficient evidence of kernel/loader upgrade support.

After that and the local restore check (with automatic Nextcloud upload), apply the rehearsed migration from
rescue media. Select the new firmware entry once. Hardware acceptance requires
encrypted-root/FIDO2 unlock, desktop login, documents and credentials, Home
Manager/Nix, networking, graphics, suspend/resume, and an actual update/rollback.
Only then select the new default, remove GRUB/rEFInd and retire the old OSTree
root. Retain shim/MokManager, the module-signing MOK and rescue media.

Once accepted, set `VERSION` to `0.9.0`, update the installation/recovery guides,
and use the existing paired release proposal and protected approval/signing
process. Publish only the exact qualified images, installers, checksums,
signatures and evidence. Describe this workstation procedure as specifically
qualified; do not advertise a universal in-place upgrader.

## Upstream XBOOTLDR follow-up, 2026-11-18 UTC

The limitation above is specific to the tested bootc 1.17.1, not all current
upstream development. GitHub API verification confirms
[bootc PR #2573](https://github.com/bootc-dev/bootc/pull/2573) merged on
2026-11-11 at `8275daa9227f7c4ee893c0b05b4134dc2ff11283`. It implements VFAT
XBOOTLDR selection for native systemd-boot install, upgrades, rollback,
finalization and garbage collection while retaining the loader on the ESP.

The latest published release at this check is 1.17.4 (2026-11-04). GitHub's
commit comparison confirms it is an ancestor of that merge and does not contain
the change. Our failed 1.17.1 probe remains valid; the earlier suggestion that
we must invent the missing XBOOTLDR implementation was too broad. The selected
upstream implementation is now integrated in the installer and installed OS,
and fresh placement and boot pass as recorded below. Changing only the canonical
importer would not update either installation or runtime behavior.

BlueBuild already builds Finite's recipes. It can distribute the selected bootc
implementation, but an image recipe cannot add this missing runtime capability
to an unchanged bootc binary. The separate OSTree-to-native coexistence and
encrypted-root/subvolume discovery gates remain unproved.

## Scope selected for the upstream fix

The operator selected a pinned upstream implementation with a transition to
the first qualifying official release after 1.17.4 (1.17.5 or later), and
limited this phase to fresh installation and successful boot. No new VM update
or rollback cycles are required for this phase. Workstation coexistence and
migration design follow only after that validation; its XBOOTLDR will be created
by the operator after the workstation-specific path is derived. No hardware
partition changes are part of the runtime integration.

`sources/bootc-runtime.json` temporarily selects the merged upstream source,
without carrying a downstream Rust patch. A native Fedora RPM is built with
one compiler job in a 2 GiB container. Its low RPM release number permits
replacement by an official distro package, rather than installing a permanently
higher synthetic version. Both recipes install this RPM before generating the
native initramfs. The canonical OCI importer remains the independently pinned
1.17.1 verification tool; it is not the installer or installed OS runtime.

The daily official-release updater verifies a stable version at least 1.17.5,
resolves its tag to an immutable commit, proves ancestry of the required fix,
and checks the archive's declared version before changing the source hash. It
proposes a normal protected PR using the official version tag, preserving
reproducibility without remaining on a snapshot commit indefinitely. The live
upstream check currently leaves the snapshot unchanged because 1.17.4 is latest.
