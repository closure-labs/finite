# CI reliability and optimization review

## October 14 implementation and rollout

The latest review sampled 150 runs from October 12-14 and examined step timings
and selected logs at `c046edd3`. Successful publication took 96 elapsed minutes
and 342 summed job minutes. Qualification took roughly 49-66 minutes per profile;
the daily four-channel audit consumed 66 summed job minutes. These numbers are
observed durations, not billed usage or measurements of the changes below.

The implementation pins the installer Secure Boot certificate locally, validates
recipes before constructing images, skips builder cleanup on candidate resume,
and checks publication eligibility before expensive qualification. Fresh install
and predecessor upgrade/rollback now run independently; both applicable phases
and their desktop-security receipts remain required before promotion.

The cache setup explicitly applies the centralized public substituters to
non-flake consumers. Main checks write source-sensitive snapshots; maintenance
retains two main snapshots and leaves PR/merge-queue caches alone. Legacy main
snapshots survive until two new generations exist. Cache publishing runs
separately after successful trusted main CI, realizes its allowlisted roots
before exposing the Cachix write credential, and excludes image/VM disk stores.

SecretSpec declares the following switches and resolves GitHub environment
values or local pass entries through task-specific scopes. Enable the following
repository variables only after matching hosted benchmarks
and correctness checks pass. Their default is disabled.

| Variable | Pilot behavior |
| --- | --- |
| `FINITE_OPTIMIZED_CACHES` | Small jobs restore Nix source downloads instead of the full checks store |
| `FINITE_CACHIX_WRITER` | Publish bounded check proofs and pinned tool closures using `CACHIX_AUTH_TOKEN` |
| `FINITE_REUSE_INVENTORY` | Reuse authenticated immutable inventory, then refresh Grype and policy results |
| `FINITE_GRYPE_DB_CACHE` | Cache DB transport bytes; mandatory database refresh and freshness checks still run |
| `FINITE_QUALIFICATION_REUSE` | Reuse identical successful qualification for at most 24 hours; promotion rechecks age |
| `FINITE_QUALIFIED_ISO_PRESERVATION` | Preserve pristine qualified ISOs for seven days, retaining two successful generations per profile |

Inventory reuse binds the image/platform digest, native file hashes, tool
versions, policy/probe implementation and current policy. Old or incompatible
inventories rebuild; corrupt evidence fails visibly. It never reuses a passing
security verdict for daily audits or releases. The existing recent-resume
results path remains separately constrained by its original freshness limits.

Qualification reuse binds the exact candidate and predecessor, source/build
identity, installer certificate/hook, test implementation, runner tool versions
and firmware. New candidate digests always run fresh tests. Forced qualification
bypasses reuse. Successful evidence retains its original qualification time.
Neither signing keys nor personalized VM disk/install media enter caches.

Run **Benchmark CI cache lanes** at one revision to compare baseline, source-only
and no-cache setup for three pinned tool closures with three repetitions each.
Reports include setup/realization time, bytes, closure size and disk measurements.
Use scanner phase timings and VM timings alongside those reports. Retain the
baseline cache lane until complete job savings exceed restore/save overhead.
The observed 1.75 GB cache took about 76-102 seconds to restore, mostly extraction;
that is an upper bound on avoidable restore time, not a promised saving.

ISO preservation and qualification reuse should be exercised on one channel
before broader rollout. The exact release path takes the pristine ISO recorded
by qualification. During the disabled pilot, an explicit standalone `iso_run`
retains the legacy release path and records whether its bytes match the qualified
ISO; regenerated bytes must not be described as that exact qualified artifact.
Missing preserved evidence fails rather than silently downgrading the exact path.

Local tests cannot establish Secure Boot acceptance or hosted publication savings.
The hosted tool setup measurements below validate the smaller cache lane;
production publication wall time and summed job savings remain unmeasured.

### Hosted validation on October 14

The [matched hosted cache benchmark](https://github.com/closure-labs/finite/actions/runs/38610456587)
passed all 27 measurements and its aggregate at `1a0bedf13cd3`. Each cell below is
the median of three fresh hosted runners, including Nix setup/cache restore and
the first tool realization. The tool closures and lockfiles matched across lanes.

| Tool closure | Baseline store cache | Source-only lane | No Actions cache | Baseline to source-only reduction |
| --- | ---: | ---: | ---: | ---: |
| Image tools | 94.72 s | 29.31 s | 33.22 s | 65.41 s |
| Scanner tools | 97.19 s | 28.88 s | 33.41 s | 68.31 s |
| Repository audit | 104.01 s | 27.50 s | 28.88 s | 76.51 s |

Same-run warm realization medians ranged from 0.99 to 1.29 seconds. The baseline
restored the existing 1.75 GB main store archive. Source caches were unseeded, and
branch jobs cannot save trusted main snapshots. These results validate avoiding
the oversized store restore for small jobs; warmed source-cache benefit remains
unmeasured. Full benchmark job medians were 120/121/133 seconds for baseline
image/scanner/audit tools and 39/38/39 seconds for the source-only lane, including
measurement diagnostics and post-job handling. Production jobs need their own
elapsed comparison. GitHub supplied two Ubuntu runner-image versions despite
matching source, Nix version and tool closures. Network counters include concurrent
runner traffic. Successful package transfers used `cache.nixos.org`; Finite Cachix
writer savings remain untested. Enable `FINITE_OPTIMIZED_CACHES` only with this scope:
small jobs use the source lane, while aggregate checks retain their store cache.
The other reuse and writer pilots still require their own rollout evidence.

Hosted startup caught two defects that local lint and mocks missed. The initial
run rejected repository `vars` inside the composite action; callers now bootstrap
the six public variables and SecretSpec validates their runtime values. VM jobs
then showed that the pinned installer lacked OpenSSL; the host now generates and
checks DER in a temporary context, and the container copies the validated bytes.
Tests cover all option callers and context cleanup after successful or failed
container builds. The complete local `ci-checks` suite passed after these fixes.
The Docker test fixture uses its actual interpreter path so it also runs inside
the Nix sandbox; hosted jobs use real Docker and were unaffected by that fixture.

All four diagnostic qualifications passed at `596b3e420433`. Each required fresh
installation, upgrade and rollback, then successful aggregation of both desktop
receipts. The final schema 2 receipts verify Secure Boot, encrypted root, exact
candidate/predecessor binding, identical runner firmware/tool/test contexts and
preserved rollback checksums. They are explicitly validation-only and cannot
authorize production promotion or evidence reuse.

| [Kernel PR 112](https://github.com/closure-labs/finite/actions/runs/35340872796) | Five tests read the advancing production lock but assume a fixed older kernel, then reject their fixture as a downgrade | Use independent kernel/policy/key fixtures and exercise freshness boundaries and failed downloads |
| [September 21 kernel monitor](https://github.com/closure-labs/finite/actions/runs/35604164790) | The blocked kernel PR leaves an approved update unapplied beyond seven days; September 19-20 fail for the same reason | Preserve the alarm, report versions and age, fix PR validation, then review and merge the update |
| [September 14 checks](https://github.com/closure-labs/finite/actions/runs/34859232944) | GitHub returned HTTP 504 for a pinned Nix input archive | Retry recognized transport failures up to three times; fail tests, evaluation, authentication and integrity errors promptly |
| [September 10 inspection](https://github.com/closure-labs/finite/actions/runs/34479360647) | Pulling the DX image exceeded the old timeout, returning 124 | The existing checkout already allows three 15-minute pulls and records phase timings; retain and measure that change |

The follow-up also fixes ISO selection after reruns: VM acceptance chooses the
newest nonexpired attempt for the verified ISO run, instead of requiring exactly
one artifact. Kernel update jobs no longer install Nix only to map a secret;
that step took 41 seconds in the September 21 run. The token remains restricted
to credential validation and PR creation.

Keep the daily full image build: floating DNF and BlueBuild module inputs are
outside Nix payload identities. Keep conservative selection, serialized channel
promotion, signature checks and the required gate. Gather cold/warm phase
timings before adding caches or runner capacity; the sampled bootstrap failures
do not justify either expense.

Two follow-ups remain: a queued main publication can be superseded by a later
documentation-only push, leaving image reconciliation to the next four-hour
poll; consider selecting trusted main builds from public image identities to
close that delay. Also, the CLI's Docker signing retry does not retry Buildx
registry transfers. Measure actual transfer failures before adding a bounded
build/export retry. Neither issue is fixed by increasing blanket test retries.

These changes are based on current main and incorporate the kernel 7.2.5 lock
from PR 112 without restoring that branch's older flake inputs. Validate the
combined revision before merging. Repeating an old failed run uses its old
source. Local regression/lint checks cannot establish that hosted image
publication or Secure Boot acceptance passes; exercise the four profiles on
GitHub before claiming rollout success.

## Confirmed causes and changes

- [August 31](https://github.com/closure-labs/finite/actions/runs/33417839486)
  and [September 7](https://github.com/closure-labs/finite/actions/runs/34136587582)
  Determinate updates failed because release lookup lacked `GH_TOKEN`.
  The resolver now receives the built-in token explicitly and uses bounded,
  authenticated GETs; local invocation can use existing `gh` authentication.
- [PR 102 validation](https://github.com/closure-labs/finite/actions/runs/34137013478)
  rejected `devenv.lock` without a final newline. Lock generation now normalizes
  final newlines before calculating changes; updater workflows validate text
  before creating a PR.
- Parent updater timeouts were 20-30 minutes, shorter than their possible child
  validation. The parent now allows 210 minutes and each child wait 180 minutes,
  covering the 5-minute selection/docs, 45-minute checks, 120-minute images and
  5-minute gate budgets, plus limited queue overhead. The parent still bounds
  total runtime if preprocessing or runner queueing takes too long.
- The release updater now distinguishes absent branches/HTTP 404 from outages.
  Only confirmed absence reports successful no-change. Downloads retry transient
  errors within a fixed budget and leave existing pins intact on failure.
- Trusted updates reuse PR or manual validation for the same branch and commit.
  Failed validation emits a direct run link and cannot enable auto-merge.
  The CI gate reports prerequisite failures without cascading missing-matrix
  errors, while still blocking the merge.
- `devenv.lock` previously took the unknown-path fallback, forcing four images
  during paired lock updates. It and the updater HTTP helper now select checks
  only; changes to `flake.lock` still compare image payload dependencies.
- Default workflow tokens for the updaters and Dependabot queue now have only
  contents-read permission. PR/merge operations retain their dedicated token.

## Validation and rollout

Hermetic tests exercise credential absence, malformed releases, failed and empty
downloads, retry limits, rate-limit budgets, lock normalization, unchanged
updates, upstream absence versus outages, validation reuse and failure gates.
Run `nix develop --accept-flake-config --command nix build --accept-flake-config --no-link .#ci-checks`.
Python analysis and test commands should also run inside `nix develop`.

After integration, dispatch fresh updater runs against the fixed main revision;
rerunning an old failed run executes its old workflow revision. Let normal
flake-update automation refresh PR 102. Confirm source resolution, generated
text checks, child validation and merge protection before comparing subsequent
runs to this baseline. No post-integration performance improvement has yet been
measured.
